# Gnomcode independent product and market audit

Date: 2026-11-01. Baseline: `617e07c`. This is a time-bounded, risk-based review, not a certification or a claim that every path was exercised. Findings come from source inspection and the checks below; existing claims and historical session logs were treated as leads, not proof. Severity combines likely impact and scope, not proof of exploitability.

## Scope and verification

Reviewed the local console, CLI and PTY entry points, session presentation, Remote/account snapshot paths, guardrail execution, website tests, and current release evidence. Compared selected workflows with primary competitor documentation. The web presentation suite passed (18 tests plus two presentation checks). Rust tests could not run because `cargo` is absent. No desktop, real agent login, real mobile device, production account, platform installer, accessibility audit, load test, or independent penetration test was available. Source inspection is not a substitute for those checks. This is a broad sample, not an exhaustive line-by-line review of the entire repository.

## Follow-up status

A subsequent fix changes new account snapshots to omit session titles, profile and relay records, publishes the true total and discloses the 200-session list limit. It also reports Git command failures, bounds Git output and execution time, and clarifies guardrails, metadata search and deletion. Existing cloud copies, independent security and privacy review, real-device/agent acceptance, remain open. Competitor features are opportunities, not implemented fixes. See the follow-up session record for verification.

## Findings

The entries below preserve the baseline findings; they are not all descriptions of the updated code.

### P1 — Account snapshot reports an incorrect total above 200 sessions

**Evidence:** `crates/daemon/src/sync.rs`, `build_remote_snapshot`, fetches at most 200 sessions, sets `count = sessions.len()`, and publishes that as `total_count` with `total_pages: 1`. The pagination query already returns a separate total but discards it. With 201 sessions the snapshot reports 200 and one page. This is a deterministic code finding, not a live account test. It can mislead users and consumers of synced reports. **Recommendation:** publish the actual total and explicitly represent the bounded list, or implement pagination; add tests at 200 and 201 and review downstream consumers.

### P1 — A hard stop is not a universal spending cap

**Evidence:** `crates/daemon/src/pro.rs`, `run_guardrails`, records a `hard_stop` alert for any matching rule but only adds Claude Code sessions to the blocked list. The hook is fail-open, and enforcement follows ingestion rather than an atomic provider-side billing limit. A user could interpret the generic rule/action label as blocking all agents or guaranteeing a maximum bill. The code supports neither claim. **Recommendation:** expose per-agent enforcement and fail-open/estimated-cost limitations at rule creation and alerts; use a warning-only label when actual blocking is unavailable; test each integration and failure mode.

### P1 — Optional account sync exposes more metadata than a minimal aggregate

**Evidence:** `crates/daemon/src/sync.rs`, `build_remote_snapshot`, serializes whole session, profile and relay records along with reports and quota. The snapshot is distinct from the encrypted Remote channel. This establishes the payload shape, not unauthorized access or an RLS failure. Titles, project identifiers and paths can be sensitive even without chat bodies. **Recommendation:** inventory serialized fields and destinations, minimize with explicit allowlisted DTOs, give separate informed consent and verify two-account isolation. Validate deletion and existing copies. Do not describe this payload as end-to-end encrypted or anonymous without evidence.

### P2 — Repository diff API hides failure as an empty result

**Evidence:** `crates/daemon/src/api.rs`, `repo_diff_get_handler`, converts command launch and UTF-8 failures into empty strings and does not inspect either Git exit status. An existing non-repository directory or missing Git can therefore return HTTP 200 with empty diff and status. `git diff HEAD` also excludes untracked file contents, although status lists them. This endpoint exists; this review did not establish that a current visible UI uses it. **Recommendation:** check exit status and return actionable errors, bound output and communicate precisely what is included; test a non-repository, missing Git, untracked files and large output.

### P2 — Search does not search conversation contents

**Evidence:** `web/lib/console-presentation.js`, `renderSessionList`, filters title, agent and repository/project metadata only. A user searching for words from a past conversation will not find them unless those words also appear in metadata. This is a capability limitation, not a broken filter. **Recommendation:** label the scope clearly and consider opt-in local full-text search with deletion/retention coverage.

### P2 — Deletion wording overstates what has been established

**Evidence:** `crates/daemon/src/console-app.js`, `deleteChat`, says “Permanently delete local chat history”; agent-owned records are separately preserved, and SQLite WAL/backups and later ingestion need lifecycle verification. The wording does not establish forensic erasure or deletion from agent history. **Recommendation:** specify the Gnomcode-owned scope and persistence limitations in the confirmation; verify that reingestion and backup handling match the stated behavior.

### Release risks — evidence missing, not proven defects

The code and prior artifacts do not establish actual authenticated handoffs, native permission behavior, current OS compatibility, physical iOS/Android behavior, PTY recovery, or independent Remote security. The project's `docs/LAUNCH_CHECKLIST.md` identifies acceptance gates; this audit did not independently close them. Test supported CLI versions and entitlements, laptop sleep/restart, native prompts, two-account isolation, reconnect/revoke races, and clean installations on each advertised platform. Measure performance under real concurrent loads. Do not advertise universal support, guaranteed security, or a released platform based on source and synthetic tests alone.

## Competitor comparison and opportunities

Sources are vendor descriptions, accessed 2026-11-01; no hands-on competitor evaluation was performed. Availability, pricing, platforms and implementation can change. “Gap” means no comparable user-facing workflow was found in the inspected Gnomcode surfaces, not proof that no code exists anywhere. These are opportunities for validation, not approved scope or automatic feature recommendations.

| Workflow | Competitor evidence | Gnomcode comparison and decision |
| --- | --- | --- |
| Isolated parallel work | [Conductor worktrees](https://www.conductor.build/docs/concepts/git-worktrees) describes per-workspace branches/worktrees and setup scripts. [Warp worktrees](https://docs.warp.dev/code/git-worktrees/) describes parallel isolated agents. | Gnomcode launches into a selected existing directory; no managed worktree lifecycle found. High-priority discovery: validate demand and design explicit cleanup, branch conflicts and setup safety. |
| Review and ship | [Conductor workflow](https://www.conductor.build/docs/concepts/workflow) describes diffs, checks, PRs and merge. [Warp code review](https://docs.warp.dev/code/code-review) describes review and file-level operations. | A basic diff endpoint exists, but no comparable integrated review/check/PR workflow was found. Consider read-only diff and untracked-file coverage first; validate before adding write actions. |
| Coordinated agents | [Warp orchestration](https://docs.warp.dev/platform/orchestration) describes parent/child coordination and local/cloud execution. | Multiple sessions are not equivalent to dependency-aware delegation or shared task state. Explore task ownership and completion visibility before autonomous multi-agent coordination. |
| Checkpoints and restore | [Cline task management](https://docs.cline.bot/core-workflows/task-management) describes Git-based file checkpoints. | No Gnomcode-managed checkpoint/restore workflow found. Explore explicit, reviewable snapshots with clear treatment of untracked files, secrets and destructive restore. |
| Cloud execution and PR entry points | [GitHub Copilot agents](https://docs.github.com/en/copilot/concepts/agent-capabilities/about-agents/about-github-copilot-agents) describes cloud tasks from issues/PRs; [Cursor background agents](https://docs.cursor.com/background-agent) describes remote clones and branches. | Paired Remote controls an online desktop; it is not independent cloud execution. Cloud agents would change the privacy, cost and trust model and are a strategic choice, not parity required for local-first users. |
| Mobile review | [Cursor web and mobile](https://docs.cursor.com/en/background-agent/web-and-mobile) describes PR management. | Remote covers conversations and eligible control, but an integrated mobile diff/PR workflow was not found. First validate phone reliability and safety, then test demand for read-only review. |

**Positioning assessment:** Combining official CLI workflows, local conversation continuity, cross-provider usage visibility and paired remote control is a coherent proposition. None of those elements is established as unique by this limited comparison. Competitors also offer parallel work, remote/cloud access and review. The strongest defensible differentiation is the *combination and chosen tradeoffs*, contingent on real-world validation; avoid claims of exclusivity, seamless transfer or complete privacy.

## Suggested order

1. Correct snapshot totals, make guardrail limitations explicit, and agree on the account metadata contract before relying on those surfaces.
2. Close authenticated handoff, real-phone, cross-platform and independent Remote security gates; test retention, error states and install recovery.
3. Interview users about isolation and review; prototype a minimal worktree plus read-only diff flow only after validating demand and privacy consequences.
4. Reassess orchestration, checkpoints and cloud execution against user evidence and product constraints. Record approved scope in SPEC and architectural decisions in an ADR.

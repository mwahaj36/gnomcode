# Gnomcode product, reliability and UX audit (2026-11-12)

Baseline `97b2f4a` (main). Unlike the [2026-11-01 audit](APP_AUDIT_2026-11-01.md), this pass exercised the **running installed app** (daemon PID 24788, `~/.spawnt/state.db`, console on `127.0.0.1:41738`) against a real Claude Code desktop-app session, real Antigravity and Codex histories, and the source. It did not run `cargo test`, macOS/Linux, or a physical phone.

## 0. Verdict in one paragraph

Gnomcode has a lot of careful plumbing (E2EE Remote, tombstones, redaction, trust labels) and very little of what a user sees in the first 60 seconds: their current chats, their limits, and a reason to keep the window open. The two things the user complained about are both real and both have concrete root causes: **(1) the app cannot find Claude Code when it comes from the Claude desktop app, and hides existing chats behind a launcher screen, and (2) there is no quota source at all for Claude Code or Antigravity**; the only limits shown are Codex, and those are stale. Engineering effort has been going into breadth (7 adapters, Remote, sync, scheduling, failover, Teams schema) while the core loop stays unreliable: 72 of 240 commits since October are `fix:`. To become production grade, stop adding surface, and make three things excellent: **see every session, see every limit, act on one session**.

## 2. Structural problems behind the bugs

1. **Scope far exceeds verified depth.** 7 adapters, launcher, PTY, chat, handoff, failover, scheduling, Remote E2EE, account sync, push, Teams schema, marketing site. SPEC §5 marks nearly every row "remaining: real acceptance". Most bugs come from features that work in tests but were never run against the user's actual setup (desktop-bundled Claude, Antigravity IDE plus CLI, multiple windows).
2. **Monolith files.** `api.rs` 4,056 lines, `store/src/lib.rs` 4,253, `remote.rs` 2,117, a 1,745-line hand-written `console-app.js` with string-built HTML. Changes collide and regress; 30% of recent commits are fixes.
3. **Two UIs for one product.** The local console (vanilla JS in `crates/daemon/src`) and the web console (`web/`, React) duplicate presenters with different conventions (D5, D10). ADR 0006/0007 accepted this; it is now the main source of inconsistency.
4. **Polling everywhere.** 2 s full ingest, 2 s foreground quota refresh, 1 s automation tick. Nothing is event-driven, so it is slow to reflect reality and expensive at rest (D3).
5. **Truth labels instead of truth.** The UI says "Inferred from recorded activity; this does not confirm a process is running" rather than checking the process. Users want the answer, not the disclaimer. Use process scan (`crates/platform` already has one), PTY ownership and hooks to *know*, and keep disclaimers for when you genuinely cannot.
6. **No fixtures for current agent versions.** Claude Code 2.1.321 from the desktop app, Antigravity IDE/CLI split, `custom-title.json` sidecar directories: each new vendor release is found by the user, not by CI.

## 3. Limits: how to do it properly

Competitors already show these numbers, so they can be obtained.

### Claude Code (exact, officially exposed)
- **Status line feed (best, official).** Claude Code pipes JSON to a configured `statusLine` command, including `rate_limits.five_hour` / `rate_limits.seven_day` with `used_percentage` and `resets_at` (epoch s), for Pro/Max, after the first response. Ship `gnomcode statusline` as an opt-in integration via the existing `gnomcode integrate claude` (backup + `--remove`, invariant 2), have it forward the payload to the daemon over the 50 ms fail-open IPC (invariant 3), and **chain** to any user status line rather than replacing it. Basis `exact`. Known gaps: windows omitted rather than null, no per-model weekly window, drift across concurrent terminals; store per observation with `observed_at`.
- **Exhaustion events from transcripts (zero-config fallback).** Parse API error / "usage limit reached" records in the JSONL for `exhausted_until` with the reset time. Basis `exact` for exhaustion only.
- **Estimated 5-hour block (fallback).** ccusage-style block reconstruction from recorded tokens. Basis `estimated`, never shown as a percentage of an unknown cap; show "~X tokens this block, resets ~HH:MM".
- **The pool is shared beyond Claude Code.** Pro/Max limits are one account-wide pool covering claude.ai chat, the Claude desktop and mobile apps, and Claude Code. Gnomcode only sees Claude Code transcripts, so any estimate built from local tokens **systematically undercounts**: a user can be at 90% from chats while Gnomcode estimates 20%. This is why the status line feed (which reports the account-wide percentage) must be the primary source, and why the token-based fallback must never be shown as a percentage or used to trigger failover/resume. Label it "Claude Code activity only; chats on claude.ai also count". The same applies to Antigravity (IDE, CLI and Agent Manager share one quota) and Codex (CLI, IDE and ChatGPT Codex share one pool), which the exact sources already account for.
- Do not read OAuth credential files (SPEC §3.8 forbids it). That rules out the OAuth usage endpoint some tools use, and that is fine given the status line feed.

### Antigravity (exact from its own process)
- Antigravity keeps quota in its local language server (`quota_manager.go: doRefreshQuota` in `~/.gemini/antigravity-cli/cli.log`). CodexBar lists Antigravity as a "local language server probe" and groups it into pools (Gemini Pro/Flash vs Claude/GPT-OSS). Implement the same read-only probe in `crates/platform`: discover the running language server process and its loopback port, call its user-status method, map `remainingFraction` + `resetTime` per model into **pooled** quota rows. Gate it behind an explicit setting (it talks to another app's local API), fail open, and label it `api`. Put the probe's path/method strings in `obfstr!`.
- Caveat to show users: Antigravity's own forum reports its quota display can be wrong (always 100%, 5-day refresh on Claude models). Cross-check against observed `RESOURCE_EXHAUSTED` errors in transcripts and prefer the error when they disagree.
- This requires updating SPEC §2/§3.9 and probably an ADR (new local data source).

### Presentation (all providers)
One Rust model: `provider -> pool -> window {used_pct, remaining_pct, resets_at, observed_at, basis, state}`. One component: bar, "% left", reset countdown, "seen N min ago", state chip (`OK`, `LOW`, `EXHAUSTED`, `RESET - AWAITING`, `UNKNOWN - enable source`). Put a compact version in the tray tooltip, the conversation header, and the Remote header. When unknown, the cell offers the one-click fix ("Enable Claude limits") instead of "Unknown".

**Positioning recommendation:** "The Windows-first, cross-agent cockpit: every session and every limit from Claude Code, Codex and Antigravity in one tray, and when one runs out, continue in another with context." Limits + live session list + handoff is something no single competitor does across Claude, Codex and Antigravity on Windows. Remote is table stakes now; keep it, but do not make it the headline or the paywall.

## 5. UX and experience redesign

**Information architecture** (today: Dashboard, Workspace, Usage, Limits, Projects, Automations, Profile = 7 places):
- **Home** = live board: sessions grouped *Needs you* (waiting for approval/question) / *Running* / *Recent*, each card with agent, project, model, elapsed time, context fill and the provider's limit bar. This is the screen people keep open.
- **Conversation** = chat + terminal tab + files/diff tab. Imported sessions get "Open in Claude/Antigravity" and "Continue here" (resume via native ID) instead of a read-only dead end.
- **Usage** (merge Dashboard, Usage, Limits, Projects): limits on top, spend/tokens below, filter by project.
- **Settings** (merge Profile, Automations, Devices).

**Tray (primary surface on Windows):** icon badge for "needs you" count; popover with per-provider limit bars and live sessions; click a session to focus its window. Most users never need the full window.

**Notifications that earn their keep:** agent waiting for approval, turn finished after more than N minutes, limit at 80% / exhausted with reset time, limit reset ("Claude is available again"). Nothing else. Rate-limit and group them (notification spam was a recent bug).

**First run:** detect installed agents (including desktop-bundled Claude), import history, show the live board within 5 seconds with real data, then offer 2 opt-ins: "Enable Claude limits" (status line integration) and "Enable Antigravity limits" (probe). No 4-step modal over a loading screen.

**Copy and density:** replace hedging paragraphs ("Inferred from recorded activity; this does not confirm...") with a single status chip and a tooltip. Prefer "42% left · resets 3:10 PM" over "Latest received snapshot. Providers update limits when they emit usage."

**Visual polish:** the console is black-on-black with 11-12 px gray text and large empty regions (Limits page). Adopt a real component system in one UI codebase (see 6.3), card elevation, a status color scale (green/amber/red for limits), and keyboard palette (Ctrl+K: jump to session, new session, switch model).

**Performance budget (advertise once measured):** daemon idle under 1% CPU and under 60 MB; new transcript line visible in UI under 1 s; cold start to live board under 2 s.

## 6. Roadmap to production grade

### Phase 1: make the core loop correct (1-2 weeks)
1. D1 desktop-bundled Claude detection + version display.
2. D3 watcher-driven ingest, stat fast path, idle back-off. Add a CPU/RSS regression check.
3. D6 presence from process evidence; delete the 24 h limit.
4. D7/D8 Workspace opens on the list; fix rail overlay.
5. D4/D5 single Rust quota-state model and one limits component.
6. Fixtures for Claude Code 2.1.x desktop transcripts and current Antigravity IDE/CLI.

### Phase 2: limits that competitors can't match on Windows (2-3 weeks)
1. Claude status line integration (opt-in, chained, fail-open), transcript exhaustion events, estimated block fallback.
2. Antigravity language-server probe (opt-in, ADR), pooled display, error cross-check.
3. Tray popover with all limit bars + reset notifications.
4. Failover/handoff driven by these limits, demonstrated end to end (Claude exhausted, continue in Codex).

### Phase 3: consolidate and cut (2-4 weeks)
1. One UI codebase: build the local console from `web/` (React) and serve the static build from the daemon; delete `console-app.js`. Kills the D5/D10 class of bugs.
2. Split `api.rs` / `store/lib.rs` by domain (sessions, quota, conversation, remote, automation).
3. Freeze or remove features without acceptance evidence: Teams schema, Cursor/Aider/Cline adapters (keep as "experimental" toggles off by default), scheduled messages, account metadata sync. Fewer, finished features.
4. Branch protection on `main`, required CI, release smoke test that launches the packaged app and checks D1-D8 against fixtures.

### Phase 4: differentiate
Worktree-per-session parallel runs with diff review; "Continue here" for imported sessions; handoff quality evals; Remote on a physical phone with push; then pricing.
